### 마일스톤 2 가 실제로 만든 것

**모임을 미리 만들어 두면 동아리 회원이 참가/불참을 누르고, 시각이 되면
참가한 사람들이 그대로 그날의 명단이 된다.**

```
tournaments        + starts_at   timestamptz          모임 시각. NULL = 즉석 모임
tournament_members + rsvp        invited|going|declined

create_session      동아리 회원 **전원** 을 심는다 (전에는 운영진만)
                    만든 사람만 going, 나머지는 invited
                    + p_starts_at (맨 뒤 default null)
set_my_rsvp         본인 행만 · 모임에서만 · 멱등
tm_fill_rsvp        대회 행은 언제나 going (트리거)
```

화면: `src/lib/rsvp.ts` · `features/tournament/SessionRsvpPanel.tsx` ·
`CreateSessionPage`(시각 입력) · `TournamentPage`(시작 전/후 분기) ·
`SessionMatchCreatePage`(참가자 먼저)

#### 판단 넷 — 다시 논하지 말 것

1. **크론이 필요 없다.** 미리 심어두고 상태만 바꾼다. 시각이 되면 화면이 바뀔 뿐
   데이터는 이미 준비돼 있다. **서버는 시각을 판단하지 않는다** — 화면이 사용자
   시계로 판단한다. 시간에 의존하는 서버 상태 전환은 시계가 어긋나는 순간
   디버깅이 불가능해진다
2. **미리 심는 것은 선택이 아니다.** `tournaments_select` 가
   `is_tournament_member(id)` 뿐이라, 안 심으면 동아리 회원에게 **모임 자체가
   안 보이고** 참가 버튼에 도달할 수 없다
3. **참가는 게이트가 아니라 기본값이다.** 안 누르고 온 사람도 경기에 넣을 수
   있다. 누르지 않으면 못 치게 하는 앱은 동아리에서 미움받는다
4. **`rsvp` 는 모임 전용.** 대회 행은 트리거가 항상 `going` 으로 맞춘다.
   대회 화면에서 이 컬럼을 읽으면 안 된다

#### 하지 않은 것

- **반복 일정(매주 화 20:00 자동 생성)** — 아무도 안 오는 유령 모임을 매주
  만들어낸다. 손으로 만드는 게 실제로 귀찮은지 보고 판단한다
- **정원 마감** — 코트를 넘으면 더 기다릴 뿐이지 못 오게 할 일이 아니다
- **참가 마감 시각** — 늦게 누르는 게 정상이다
- **`starts_at` 검증** — 과거 시각도 받는다. 어제 친 모임을 나중에 기록하는 게
  정상 경로다. "미래여야 한다" 를 서버가 우기면 시계가 어긋난 기기에서
  정상 개설이 막힌다

#### 화면이 틀리기 쉬운 자리 (smoke 61항목이 확인한 것)

- **`42501` 은 "권한 없음" 이 아니라 "이 모임 명단에 당신이 없다"** 다.
  명단은 **생성 시점 스냅샷**이라, 모임이 열린 뒤 동아리에 들어온 사람이 여기
  걸린다. `toUserMessage` 의 공용 표를 고치지 말고 `lib/rsvp.ts` 에서 덮는다
- **계정 없는 회원(`user_id is null`)을 '미정' 으로 세지 마라.** 누를 주체가
  없어서 매주 유령 미응답자가 잡힌다. `countRsvp` 가 네 칸으로 센다
- **`hasStarted` 는 못 읽는 값을 `true` 로 본다.** `false` 면 값이 깨진 순간
  아무도 빠져나올 수 없는 대기 화면에 갇힌다
- `starts_at` **직접 PATCH 는 RLS 로 0행이 걸러져도 200 + `[]`** 다.
  상태코드가 아니라 반환 행 수로 판정할 것

**계정 없는 사람이 동아리 상시 링크로 그날 모임 명단에 스스로 들어온다.**
운영진 타이핑 0회.

```

tournament_members + is_guest     화면 배지·상한 계산 전용. 권한 판단에 안 쓴다

guest_sessions(p_code)                        anon. 후보 모임 목록 (필드 셋만)
join_as_guest(p_code, p_session_id, p_name)   anon. 등록
```

화면: `/g/:guestCode`(로그인 가드 **밖**) · `ClubPage` 링크 발급·재발급 ·
`MembersPage` 게스트 배지 · `src/lib/guest.ts`(봉투 파싱)

검증: `db:smoke:guest` **1~67절** · 회귀 전량 통과
(club 89 · security 37 · rsvp 61 · match 44 · session 23 · roster 23)

> 마일스톤 4 가 같은 스크립트에 68~85절을 이어 붙여 지금은 **85절**입니다.
> 85절이 "1~67절이 여전히 67/67 로 통과한다" 를 되읽으므로, 위쪽 절을 늘리거나
> 줄이면 거기서 걸립니다 — 문서의 절 번호가 정본이 아니게 되는 것을 막는 장치입니다.

#### 판단 다섯 — 다시 논하지 말 것

1. **RLS 정책을 하나도 안 만든다.** `is_direct_api_call()` 은
   `current_user = 'authenticated'` 하나로 정식 경로를 가르는데, anon 은
   `'anon'` 이라 **거짓**이 된다. 그 순간 `guard_tournament_update` ·
   `guard_member_update` · `guard_member_delete` 가 전부 "RPC 경로다" 로
   오판해 통과한다. **anon 에 정책을 하나라도 열면 관리자에게도 막힌
   `owner_id` · `role` · `user_id` 변경이 anon 에게 열린다.** definer 함수
   둘에만 grant 하고, 문제가 생기면 `revoke` 한 줄로 닫는다
2. **레이트리밋을 만들지 않는다.** `join_attempts.user_id` 가
   `not null references auth.users` 라 계정 없는 사람은 기록할 수 없다.
   억지로 풀면 카운터가 전 세계 anon 하나로 합쳐져 **열 번 틀린 한 사람이
   모든 게스트를 잠근다**(전역 차단 DoS). 대신 22자 엔트로피 + 모임당 상한 60
3. **그 상한이 유일한 방어선이라 카운트-삽입을 직렬화한다.**
   `pg_advisory_xact_lock(hashtextextended(session_id))`. 코트 앞에서 여럿이
   동시에 링크를 여는 건 정상이고, 락이 없으면 전부 같은 숫자를 읽고 통과한다.
   `tournaments` 행을 잠그지 않는 이유는 같은 모임의 다른 쓰기(경기 시작)와
   경합하기 때문
4. **게스트를 지우지 않는다.** `guard_member_delete` 가 출전 기록 있는 행을
   막아서, 자동 삭제를 켜면 뛴 게스트는 남고 안 뛴 게스트만 사라진다 —
   **결과가 반반인 삭제는 규칙이 아니다.** 그리고 `tournament_members` 는
   원래 모임 하나에 묶인 테이블이라 다음 주는 새 행 집합이다. 지울 것이 없다
5. **`user_id is null` 로 게스트를 판별하지 않는다.** `create_session` 이
   미가입 회원(매주 오는 사람)도 심으므로, 그걸로 배지를 그리면 그 사람들
   전원에게 게스트 딱지가 붙는다. `is_guest` 가 그 둘을 가른다

#### 게스트가 쓰기를 못 하는 것은 코드 0줄로 이미 관철돼 있다

- **심판 불가** — `guard_referee_has_account`(`roster.sql`)가 `user_id is null`
  인 멤버의 심판 지정을 이미 거부한다
- **점수 불가** — `is_match_player` 가 `tm.user_id = auth.uid()` 를 요구한다.
  NULL 은 매칭되지 않고, `auth.uid()` 도 NULL 이면 `NULL = NULL` 은 true 가
  아니라 NULL 이라 `exists` 가 거짓이다. 이중으로 안전
- **나머지 RPC 불가** — anon 에게 grant 가 없다. 정책 이전에 grant 에서 끝난다

#### 판단 일곱 — 다시 논하지 말 것

1. **정책 0개는 읽기라고 달라지지 않는다.** "쓰기니까 위험했던 것" 이 아니다 —
   `is_direct_api_call()` 의 붕괴는 **롤에서 오지 동작 종류에서 오지 않는다.**
   읽기 정책 하나를 anon 에 열면 그 정책이 **PostgREST 직접 조회에도 그대로
   열린다.** 마일스톤 3 의 판단 1 이 글자 그대로 다시 적용된다
2. **무게는 SQL 줄 수가 아니라 반환 필드 목록에 있다.** 명단 전체
   (`tournament_members`)를 실으면 링크 하나로 그날 온 사람 **전원의 표시명**이
   나가고, `profiles` 를 비공개로 지켜 온 것이 그 한 필드로 무의미해진다.
   **코트에 편성된 사람 이름만** 나간다. 게스트가 알아야 하는 것은 "지금 코트에서
   누가 치나" 이지 "오늘 누가 왔나" 가 아니다
3. **`match_overview` 를 참조조차 하지 않는다.** (1) 뷰가 실어 나르는 필드가
   싣기로 한 것보다 훨씬 많아 "필드 하나가 곧 노출 표면" 이라는 규율이 첫 줄에서
   무너지고, (2) `security_invoker` 뷰의 권한 해석이 **함수 소유자에 따라 갈린다** —
   보안 경계를 배포 시점 값 위에 세우지 않는다. 테이블을 직접 조인해 컬럼을 명시한다
4. **Realtime 은 원리적으로 불가.** 구독은 **구독 롤의 RLS 를 그대로 타므로**
   anon 에 열려면 `matches` 에 anon 정책이 필요하고, 그 정책은 위 1 과 똑같이
   직접 조회에도 함께 열린다. 폴링 10초다 (앱 전역 `staleTime` 과 같은 값)
5. **오류를 하나로 합친다** (`board_closed`). 다른 동아리의 session_id · 대회 UUID ·
   시각 창 밖 · 없는 id · 코드와 세션의 불일치가 **전부 같은 코드**로 돌아온다.
   갈라 주면 임의 UUID 로 "이 동아리에 이 모임이 있나" 를 캐는 탐색기가 된다
6. **서버는 순번을 세지 않는다.** 셈법이 이미 SQL `notify_up_next` 와 화면
   `queuePosition` 둘이고 **둘은 같은 줄을 세야 한다.** 셋이 되면 어긋날 자리가
   셋이다. 서버는 `queue_order` 만 싣고 정렬해서 보낸다
7. **이름은 localStorage 에 있고 강조 전용이며 서버로 안 간다 — 권한이 아니다.**
   `guest_board` 는 이름을 인자로 받지 않는다. **이름이 없어도 현황판은 완전하다.**
   이미 받은 목록과 문자열을 맞춰 볼 뿐이라 명단 탐색 도구가 되지도 않는다 —
   애초에 명단을 안 받기 때문이다

#### 하지 않은 것

- **끝난 경기 목록** — `finished_count` 숫자 하나만 싣는다. 게스트의 질문은
  "지금" 과 "다음" 이고, 지난 기록은 로그인 사용자 화면의 일이다. 그리고 모임이

- **게스트 코드를 화면에 그리기** — 표시도 공유 버튼도 없다. 화면 캡처 한 장으로

- **레이트리밋** — 마일스톤 3 과 같은 이유(`join_attempts.user_id` 가 계정을

**① "anon 실행 가능 함수가 셋" 은 틀렸습니다 — 넷입니다.**

**③ 점수 표시를 `matches.scored` 로 판단하면 안 됩니다.**

`not null default true` 라 **점수를 한 번도 안 넣은 진행 중 경기도 참**이고,

```
/c/:id            허브 (게스트 링크 큰 버튼 + 산하 대회 + 문 셋)
/c/:id/guest      게스트 링크      /c/:id/members    명단
/c/:id/invite     동아리 코드      /c/:id/settings   이름 · 나가기 · 지우기
```

그 화면의 주석은 *"목록 하나(명단)와 값 두 개뿐이라 나눌 만큼 길어지지 않는다"* 고
변론했는데, 그 사이 **목록이 둘**이 되고 그 사이에 게스트 링크가 끼면서 변론이
무너졌습니다. 체육관에서 운영진이 이 화면을 여는 이유는 거의 언제나 게스트 링크를
카톡에 붙여넣는 것인데, 그게 회원 30명 명단 밑에 있었습니다.

**코드 둘도 갈랐습니다** — 동아리 코드는 명단에 영구히 남기는 코드, 게스트 링크는
오늘 하루짜리입니다. 껍데기는 `features/club/ClubScreen.tsx` 이고 `AdminScreen` 과
같은 자리입니다.

### 3~4. 무효 처리와 알림 스위치

**무효는 상세 화면에만** 둡니다. 목록의 책임은 찾는 것인데 카드마다 X 가 붙어 있어서,
폰에서 훑다 **손끝이 스치는 자리가 곧 "순위에서 빼기"** 였습니다. 그 버튼 하나 때문에
카드 여백(`pr-14`)까지 비틀어 놨었고, 실패 문구는 목록 맨 위에 떠서 어느 경기
이야기인지 알 수 없었습니다. 상세 쪽은 판단 근거(점수 흐름 · 심판)가 이미 있고 누르기
전에 결과를 설명합니다. **목록 화면의 무효 테스트 4개는 상세 테스트로 옮겼습니다** —
계약이 사라진 게 아니라 자리를 옮긴 것입니다.

**알림 스위치는 `/settings/alerts` 로** 뺐습니다. 대회 셋에 참가한 사람에게는 같은
스위치가 세 군데 뜨고 셋이 같은 값을 공유했습니다 — A 대회에서 끄면 B·C 알림도 죽는데
화면은 그렇게 말하지 않았습니다. 반대로 아직 어느 대회에도 안 들어간 사람은 **켤 방법이
아예 없었습니다.** 대회 설정에는 조와 이름만 남습니다.

### 메인 화면 — 문이지 현황판이 아닙니다

### ① 모임에서 점수 제거 — 링크를 지우는 것으로는 부족합니다

> *"아예 정기모임인지 대회인지만 체크하고 점수하는걸 아예 없애. 정기모임은 그냥

점수판으로 가던 길 **넷을 전부** 끊었습니다.

```
코트 카드의 '점수 기록' 보조 링크        삭제
```

**마지막 하나가 핵심입니다.** 링크만 지우면 주소를 직접 치거나, 열어 둔 탭을

방이 없어지는 것은 아닙니다.**

**화면 안이 아니라 라우트에서 막은 이유**: 점수판은 `useWakeLock` ·
`useScreenRotation` · `useMutation` 을 여럿 부릅니다. 화면 안에서
`if (모임) return <Navigate/>` 를 하면 훅이 조건부로 불려 **훅 규칙 위반**입니다 —
실제로 걸렸습니다. 가드는 훅을 부르기 **전에** 서야 하고 그 자리는 `RequireAuth`
와 같은 라우트 층입니다 (`src/features/tournament/TournamentOnly.tsx`).

`kind` 를 **아직 모르는 동안에는 판단하지 않습니다.** '대회다' 로 넘겨짚으면 잠깐
점수판이 그려졌다 사라지고, '모임이다' 로 넘겨짚으면 회선 느린 체육관에서 대회
심판이 자기 화면에서 튕깁니다.

**덤으로 사라진 문제** — 동점으로 끝내려다 *"승리 팀을 직접 선택해 주세요"* 로
막히던 막다른 길이 모임에서 없어졌습니다. 점수를 아예 안 세니 `score_events` 가 비고
`finish_match` 가 승자 없이 끝내는 경로로 들어갑니다. **제약조건을 고치려던 작업은
필요 없어져 멈췄습니다.**

권한도 서버와 맞췄습니다. 전에는 `canScore = isAdmin || session` 이라 모임 참가자
전원에게 시작·채점 화살표가 보였는데 서버(`can_run_match`)는 **그 경기에 뛰는 사람**만
받습니다 — 눌러야 오류를 보는 상태였습니다. `src/lib/matchAccess.ts` 로 옮겨 같게
만들었습니다.

**대회는 한 줄도 안 바뀌었습니다.** 같은 대회 id 로 변경 전후를 찍어 sha256 이
일치하는 것을 확인했습니다 (35674 B, `38988f67…`).

### ② 메인 화면 — 동아리가 주인공입니다

> *"처음 메인페이지에서 내이름이랑 이런거 버튼들 너무 공간도 많이차지하고 쓸데없음"*
> · *"메인 페이지에서 모임열기가 메인이 아니라 내 동아리가기가 메인이어야함"*

화면 맨 위를 **아무도 안 쓰는 것 둘**(이름 · 로그아웃)이 차지하고 있었습니다. 자기
이름은 이미 알고, 로그아웃은 몇 달에 한 번 누릅니다. 이름은 뺐고 로그아웃은 맨 아래로
내렸습니다 — 링크가 아니라 동작이라 줄 목록 밖에 둡니다.

그리고 **한 달에 한 번도 안 눌리는 버튼이 화면 절반**이었습니다. 모임 열기(매주) ·
대회 만들기(시즌에 몇 번) · 참가하기(그보다 드묾)가 같은 크기 카드였습니다.

지금은 **동아리가 주인공**입니다. **동아리가 하나뿐이면 목록을 건너뛰고 바로 그
동아리로** 보냅니다 — 대부분이 여기 해당하는데, 고를 것이 하나뿐인 목록을 한 번 더
보여주는 것은 탭만 하나 늘리는 일입니다. 아직 동아리가 없으면 문구가 **'동아리
만들기'** 로 바뀝니다 — 그 사람에게 '내 동아리' 는 빈 목록입니다.

### ③ 뒤로가기 · 홈 — 원인은 어디로 가느냐가 아니라 손이 닿느냐였습니다

> *"뒤로가기 버튼 이거 너무 불편함"* → 고친 뒤 → *"진짜 이전만 있으니까 너무 불편해"*

**하단 탭바만 `fixed` 이고 뒤로가기가 든 머리는 문서 흐름에 있었습니다.** 명단·기록·
대진표처럼 긴 화면에서 조금만 내리면 뒤로가기가 화면 위로 사라져, 나가려면 매번 맨
위까지 스크롤해야 했습니다. **아이폰 홈 화면 추가(PWA standalone)에는 브라우저
뒤로가기도 가장자리 스와이프도 없습니다** — 알림 때문에 우리가 그렇게 안내하는데,
그 사람들에게 이 버튼이 유일한 출구였습니다.

`BackBar`(sticky) 하나로 호출 지점 22곳 · **라우트 32개**를 덮었습니다.
`fixed` 가 아니라 `sticky` 인 것이 중요합니다 — 흐름에서 자리를 그대로 차지하므로
아래 내용이 뒤에 깔리는 문제가 구조적으로 없고, 화면마다 상단 여백을 맞출 필요가
없습니다. **`BackLink` 의 동작 판단은 한 글자도 안 건드렸습니다.**

그다음 홈입니다. `HomeLink` 를 **기본 켜짐**으로 넣어 20개 화면이 한 번에 덮였습니다.
**기본값이 켬인 것이 요점입니다** — 새 화면을 만드는 사람이 출구 둘을 공짜로 받고,
끄는 쪽만 이유가 필요해집니다. 중복은 세 군데서 피했습니다.

```
대회·모임 화면(6개)   하단탭 '더보기' 에 이미 홈이 있다
홈 바로 아래 화면      뒤로가기가 이미 '메인으로' 를 가리키면 같은 버튼이 둘이 된다
게스트 화면            계정 없는 사람에게 / 는 로그인 화면이다 (테스트로 못 박음)
```

⚠ **주소만 보고 끄지 않습니다.** `/new/session?club=…` 은 동아리에서 세 단계 들어가
도달하는 경로라 거기선 홈이 정확히 필요합니다. `useCanGoBack` 으로 **매 렌더마다**
"지금 뒤로가기가 어디를 가리키나" 를 판단합니다.

홈은 `navigate('/', { replace: true })` 입니다 — **히스토리를 쌓지 않습니다.**
세 단계 들어가 홈을 누르고 폰 뒤로가기를 누르면 중간 화면으로 가지, 방금 떠난 깊은
화면으로 끌려 들어가지 않습니다.

**찍어서만 보인 것** — 관전 화면에 홈을 더하니 줄이 좁아져 '나가기' 가 세 글자로

박았습니다.

### ④ 경기 짜기 — 이미 다른 경기에 든 사람은 잠급니다

> *"코트 배정할 때 그 다른 게임 대기하고 있는 명단도 빼달라는거야"*

방금 편성한 사람이 다음 경기 후보에 그대로 남아 있어서 **한 사람이 두 코트에 동시에
불려 갈 수** 있었습니다. 규칙 한 문장 — 아직 안 끝난 경기(`live` · `scheduled`)에
선수로 이름이 올라 있는 사람은 묶여 있습니다. 판단은 `src/lib/busy.ts` 한 곳입니다.

**없애지 않고 잠갔습니다.** 12명 중 8명이 사라지면 남는 것은 4줄뿐이고, 명단을
아무리 훑어도 *"김민수 어디 갔지"* 에 답할 방법이 없습니다. 잠가 두면 *"아, 1번 코트"*
로 끝납니다. **이름 순서도 그대로 뒀습니다** — 잠긴 사람을 뒤로 몰면 순서가 바뀌어
같은 문제가 다시 생깁니다.

**진행 중과 대기 중을 갈랐습니다.** 첫 촬영에서 둘 다 `2번 코트` 로 똑같이 나와
구분이 안 됐는데, 둘은 운영이 다릅니다 — **대기는 그 경기를 지우면 바로 풀리고**,
뛰는 사람은 끝날 때까지 기다리는 수밖에 없습니다. 그래서 `1번 코트` / `2번 코트 대기`
입니다.

🚫 **심판은 세지 않습니다.** 서버(`start_match`)의 '두 코트 동시' 검사가
`match_team_players` 만 훑기 때문입니다(`20260825000002`). 여기서 심판까지 묶으면
**화면이 서버보다 좁아져** 서버가 허락하는 편성을 화면이 막습니다. 대회 편성이
나중에 이 함수를 쓰게 되면 그때는 심판도 세야 하고, 그건 서버 검사도 함께 넓히는
일입니다.

이미 고른 사람은 묶여도 누를 수 있습니다 — 고른 뒤 남이 편성해 버린 경우 잠그면
뺄 방법이 없어집니다(`exceptMatchId` 도 같은 이유로 있습니다).

## 🔴 마일스톤 3 에서 실제로 프로덕션을 깨뜨린 것 두 가지

둘 다 **정적 리뷰(DB·보안) 두 벌이 통과시켰고, 실행이 잡았습니다.**
리뷰는 "이 코드가 무엇을 깨뜨리나" 를 보고, 실행은 "실제로 되나" 를 봅니다.

### 1. `create_club` 이 `guest_code` 를 안 채웠다

`clubs.guest_code` 를 default 없이 `not null` 로 만들어 놓고 `create_club` 은
그대로 뒀습니다. backfill 은 **기존 행만** 채웠고 **앞으로 들어올 행**은
아무도 채우지 않았습니다. 적용했으면 모든 동아리 생성이 죽었습니다.

> **컬럼을 `not null` 로 만든 쪽이 채우는 책임도 진다.**
> 리뷰 지시에 "이 마이그레이션 이후 **새로 만들어지는 행**이 모든 제약을
> 만족하는가" 를 항목으로 넣으세요. 두 리뷰어 다 backfill 순서는 봤지만
> 그 질문을 안 했습니다.

### 2. `gen_random_bytes` 를 search_path 에서 못 찾았다

`gen_guest_code` 가 `set search_path = public, pg_temp` 로 잠근 채
`gen_random_bytes(22)` 를 불렀습니다. 이건 **pgcrypto** 함수이고 Supabase 는
확장을 `public` 이 아니라 **`extensions`** 스키마에 설치합니다.

```
function gen_random_bytes(integer) does not exist
```

이 함수는 `create_club` 안에서 불립니다. **게스트 기능만이 아니라 동아리
생성 전체가 막혔고**, `db:smoke:club` 첫 항목이 잡았습니다.
`20260828000002` 로 `extensions` 를 search_path 에 더해 복구했습니다.

> **확장이 설치돼 있다는 것과 내 search_path 에서 보인다는 것은 다른 말입니다.**
> `gen_random_uuid()` 가 멀쩡히 돌아 더 늦게 드러났습니다 — 그건 PG13+ 코어
> 내장이라 pgcrypto 와 무관합니다.
> **pgcrypto 함수(`gen_random_bytes` · `crypt` · `digest` 등)를 쓸 때는
> `set search_path` 에 `extensions` 를 반드시 넣으세요.**

## 확정된 결정 (다시 논하지 말 것)

1. **동아리는 명단의 원천이지 권한 축이 아니다.** 기존 권한 헬퍼
   `is_tournament_member` / `is_tournament_admin` / `is_tournament_owner` 를 한 줄도 안 건드린다.
   동아리 운영진이 산하 대회를 만지는 근거는 **생성 시점에 심어진 멤버 행**이다.
   그 귀결로 **나중에 운영진이 된 사람에게는 그 전에 열린 산하 대회가 안 보인다** — 버그가 아니다
2. **동아리는 선택 계층.** 동아리 없는 기존 대회·모임이 그대로 동작한다. 두 경로를
   유지하는 부담은 운영 중인 서비스를 안 깨는 값으로 감수한다
3. **강등만 전파하고 승격은 명단에 이미 있는 행만.** 끝난 대회와 주최자 행은 양쪽 다 제외.
   명단에 없는 사람을 심으면 대진표·순위에 뛴 적 없는 유령 참가자가 생긴다
4. **대회 명단은 동아리 명단의 복제(스냅샷), 참조가 아니다.** 가장 되돌리기 어려운 결정이다.
   참조로 몇 주 운영하면 지난 대회의 이름이 동아리의 *현재* 이름을 가리키게 되고,
   그때 그 사람이 뭐라고 불렸는지는 복원할 수 없다
5. **게스트의 신원은 본인이 적는 이름.** 시스템이 보는 사람이 누구인지 알 필요가 없다
6. **게스트는 그날 모임에만 존재한다.** 동아리 명단에 남는 것은 회원뿐.
   다만 이미 치른 경기 기록에는 이름이 남는다 — 명단에서 사라지는 것과 기록이
   지워지는 것은 다르다
7. **같은 이름은 뒤에 글자를 붙여 가르되 기존 이름은 절대 안 바꾼다.** 이름이
   대진표·심판 배지·기록 검색에서 사람을 찾는 열쇠다
8. **초대 코드는 두 종류로 두고 입구를 가른다.** `/join` 은 대회 코드, `/clubs/join` 은
   동아리 코드. 한 칸에 둘 다 받는 통합 화면은 만들지 않는다 — 누르기 전에는 어디로
   들어가는지 알 수 없게 된다. 대신 각 화면 아래에 반대쪽으로 가는 줄을 하나 둔다
9. **동아리 역할 이름을 대회 쪽과 겹치지 않게 둔다.** 동아리장·운영진·회원 /
   주최자·관리자·참가자. 한 사람이 두 축에서 서로 다른 역할을 갖는 일이 정상이라,
   같은 단어를 쓰면 지금 어느 축의 권한인지 흐려진다
10-1. **게스트 코드는 재발급한다.** 동아리 코드와 반대다. 게스트 코드는
    그날 온 사람에게 그때 보여주는 링크라, 바꿔도 "아직 안 들어온 회원에게
    뿌린 코드가 죽는" 문제가 없다. `rotate_guest_code` 가 있다
10-2. **게스트 코드와 동아리 코드는 다른 코드다.** 게스트에게 `invite_code` 를
    주면 게스트가 **회원이 되어** `club_members` 에 남는다 — 확정 결정 6 이
    링크 하나로 깨진다
10. **동아리 코드 재발급은 만들지 않는다.** 대회와 달리 코드를 바꾸면 아직 안 들어온
    회원에게 뿌린 코드가 한꺼번에 죽는다. 서버에도 재발급 RPC 가 없다
11. **anon 에는 RLS 정책을 하나도 열지 않는다 — 읽기도 예외가 아니다.** 비로그인
    경로는 전부 **정책 0개 + SECURITY DEFINER RPC** 로 간다. 지금 셋이고
    (`guest_sessions` · `join_as_guest` · `guest_board`), `is_direct_api_call()` 까지
    **정확히 넷**이 anon 이 부를 수 있는 public 함수의 전부다. 넷째는 의도된 것이고
    걷으면 주최자의 정상 수정이 막힌다. 검사는 개수가 아니라 **집합**으로 한다
    (`db:verify` · `db:smoke:guest` 81절)

### DB 작업

```bash
export SUPABASE_DB_URL="$(sed -n 's/^SUPABASE_DB_URL=//p' .env.local | head -1 | tr -d '\r')"
npx supabase db push --db-url "$SUPABASE_DB_URL" --dry-run   # 먼저 dry-run
npx supabase db push --db-url "$SUPABASE_DB_URL"
npm run db:types                                             # 반드시 이어서
```

- **`npm run db:push` 는 `.env.local` 을 안 읽습니다.** 셸 환경변수 `$SUPABASE_DB_URL` 만 봅니다.
  tsx 스크립트(`db:types` · smoke · `db:verify`)는 `.env.local` 을 직접 파싱합니다
- **pooler 가 자주 timeout 을 냅니다.** 2~3번 재시도하면 붙습니다. SQL 문제가 아닙니다
- **push 후 `db:types` 는 선택이 아닙니다.** 손으로 넣은 타입의 누락을 잡아줍니다
  (실제로 두 번 잡혔습니다 — `MatchTeamsRow.group_id` nullable 누락 등)
- **대회·모임이 진행 중일 때 적용하지 마세요.** `alter table tournaments` 가 잠깐
  쓰기 락을 잡습니다. 테이블이 작아 순식간일 가능성이 높지만 체육관에서 점수 찍는
  중에 걸리면 곤란합니다

### 🔴 `@smashtest.local` 계정을 도메인만 보고 지우지 마세요

smoke 는 **프로덕션에 테스트 계정과 대회를 만들었다 지웁니다.** 끝나면 정리하지만,
중간에 죽으면 계정이 남습니다. 여기까지는 사실입니다.

**그런데 지금 프로덕션에 있는 `@smashtest.local` 계정 중 21개는 smoke 잔여물이
아닙니다.** `npm run db:seed` 가 심은 것이고, **실제 대회 5곳의 참가자**입니다
(정기전 17명 · 상반기대회 19명 등). 도메인만 보고 일괄 삭제하면 그 명단이 날아갑니다.

진짜 잔여물은 지금 **둘**입니다 — `rosterui-admin-1787120018534@` ·
`rosterui-joiner-1787120019911@` (위 「3. 알면서 안 고친 것」 참고).

지우기 전에 **소속을 확인하세요.** 로컬 접두사로 갈립니다.

| 로컬 접두사 | 어디서 왔나 | 지워도 되나 |
|---|---|---|
| `seed-N@` | `npm run db:seed` (`scripts/seed-members.ts`) | ❌ 실제 대회 명단 |
| `demo@` | 데모 대회 주최자 (`npm run demo:live` 가 씁니다) | ❌ |
| `club-` `guest-` `match-` `session-` `roster-` `rsvp-` `sec-` `notify-` `smoke-` `pushe2e-` + 타임스탬프 | smoke 스크립트가 그때그때 만든 것 | ✅ 죽은 실행의 잔여물이면 |
| `rosterui-` | **문서가 서로 다른 말을 합니다** — 아래 상자 | ⚠ 아래 SQL 로 소속부터 확인 |

> ⚠ **`rosterui-` 두 계정은 판단이 갈려 있습니다.** `scripts/smoke-rsvp.ts` 의 정리
> 주석은 `rosterui-*` 를 `seed-*` · `demo@` 와 함께 **"사용자의 실제 대회 참가자"**
> 로 묶어 두었는데, 실제로 남은 둘(`rosterui-admin-1787120018534@` ·
> `rosterui-joiner-1787120019911@`)은 이름 모양과 타임스탬프로 보면
> `db:smoke:roster` 의 정리 실패 잔여물로 보입니다.
> **아래 SQL 로 소속을 먼저 확인하고, 행이 나오면 지우지 마세요.**

```sql
-- 지우기 전에: 이 계정이 어느 대회 명단에 들어 있나
select u.email, t.name, tm.display_name
from auth.users u
join tournament_members tm on tm.user_id = u.id
join tournaments t on t.id = tm.tournament_id
where u.email like '%@smashtest.local'
order by t.name, tm.display_name;
```

행이 나오면 그 계정은 **살아 있는 명단의 일부**입니다.
