## 도메인 규칙

```
조 개수 N, 조커조 K  →  1조~K조가 조커조로 고정
목표 점수   일반 21점 / 조커 11점       ← 대회 설정에서 바꿈
듀스        기본 꺼짐. 켜면 2점 차, 상한(기본 30/15)에 닿으면 거기서 끝
승점        일반 승리 1.0 / 조커 승리 0.5 / 패배 0
경기        조 vs 조, 복식 2명씩 (단식으로 바꿀 수 있음)
코트        한 코트에 진행 중 경기는 하나 (부분 유니크 인덱스로 DB 가 강제)
심판        관리자가 아니라 편성 때 지정된 참가자
알림        코트 대기 2번째 이하가 되면 '곧 차례'
```

전부 `tournaments.config` (jsonb) 에 있습니다. 만들 때와 관리 → 경기 규칙에서
바꿉니다. 값의 모양은 `src/lib/ruleSettings.ts`, 검증은 SQL
`normalize_tournament_config` 한 곳입니다.

## 대회와 모임

`tournaments.kind` 하나로 갈립니다. 진행 엔진(코트 · 대기열 · 점수 원장 ·
알림 · 심판 화면)은 한 벌을 같이 씁니다 — 사람·코트 단위라 그대로 쓰입니다.

```
                  대회 (tournament)        모임 (session)
목적              기록 · 순위               그날 코트 돌리기
경기의 한 편      조 (group_id NOT NULL)   사람 (group_id NULL)
점수              필수                      옵션 — 세고 싶은 경기만
경기의 끝         승자가 있어야 끝          '끝났다' 만으로 끝 (scored=false)
순위              조별 순위표               없음 (탭을 숨긴다)
심판              편성 때 지정              없음 — 뛰는 사람이 돌린다
목표 점수         조커 11 / 일반 21         일반 21 (세는 사람을 위해 그대로 둠)
만드는 함수       create_tournament         create_session
편성 함수         create_match              create_session_match
```

모임은 날짜별로 하나씩 만듭니다 (`10월 7일 모임`). 이름 기본값은
`src/lib/session.ts` 의 `defaultSessionName` 입니다.

화면이 갈리는 지점은 `src/lib/session.ts` 한 곳에 모아 두었습니다.
페이지마다 `kind === 'session'` 을 흩뿌리면 새 화면을 만들 때 하나씩 빠뜨립니다.

## 참가 신청 — 모임을 미리 만든다

동아리 밑에 모임을 **미리** 만들어 두면 회원이 참가/불참을 누르고, 시각이 되면
참가한 사람들이 그대로 그날의 명단이 됩니다.

```
tournaments        + starts_at   모임 시각. NULL 이면 즉석 모임(곧바로 진행 화면)
tournament_members + rsvp        invited | going | declined
```

```
화요일 오후   회원이 [참가] 를 누른다        모임장은 코트를 몇 개 빌릴지 안다
화요일 20:00  화면이 코트 현황으로 바뀐다     참가한 사람이 경기 짜기 목록
```

### 이 설계의 뼈대 넷

**1. 크론이 없다.** 모임을 만들 때 동아리 회원 **전원**을 `tournament_members` 에
심고 `rsvp='invited'` 로 둡니다. 참가를 누르면 `'going'`. 시각이 되면 **화면이 바뀔
뿐 데이터는 이미 준비돼 있습니다** — '추가' 라는 동작이 없습니다.

**서버는 시각을 판단하지 않습니다.** `hasStarted()` 가 사용자 시계로 판단합니다.
시간에 의존하는 서버 상태 전환은 서버 시계와 사용자 시계가 어긋나는 순간
디버깅이 불가능해집니다.

**2. 미리 심는 것은 선택이 아닙니다.** `tournaments_select` 가
`is_tournament_member(id)` 뿐이라, 안 심으면 동아리 회원에게 **모임 자체가 안 보이고**
참가 버튼이 있는 화면에 도달할 수 없습니다. 이 길은 동아리 권한 모델과도 같습니다 —
근거는 언제나 **생성 시점에 심어진 멤버 행**이지 동아리 소속이 아닙니다.

**3. 참가는 게이트가 아니라 기본값입니다.** 안 누르고 온 사람도 경기에 넣을 수
있습니다. 누르지 않으면 못 치게 하는 앱은 동아리에서 미움받습니다.

**4. 명단은 생성 시점 스냅샷입니다.** 모임을 연 뒤 동아리에 들어온 사람은 그 모임이
보이지 않고 참가도 못 누릅니다(`42501`). 의도된 동작입니다.

### 화면이 틀리기 쉬운 자리

- **`set_my_rsvp` 의 `42501` 은 "권한 없음" 이 아니라 "이 모임 명단에 당신이 없다"** 입니다.
  `toUserMessage` 의 공용 표를 고치지 말고 `lib/rsvp.ts` 에서 덮습니다 — 공용 표를
  고치면 대회 쪽 진짜 권한 오류 안내가 나빠집니다
- **계정 없는 회원(`user_id is null`)을 '미정' 으로 세지 마세요.** 누를 주체가 없어서
  매주 유령 미응답자가 잡힙니다. `countRsvp` 가 네 칸(참가·미정·불참·명단만)으로 셉니다
- **`hasStarted` 는 못 읽는 값을 `true` 로 봅니다.** `false` 로 두면 값이 깨진 순간
  아무도 빠져나올 수 없는 대기 화면에 갇힙니다
- **대회는 `rsvp` 를 읽지 않습니다.** `tm_fill_rsvp` 트리거가 대회 행을 항상 `going`
  으로 맞춥니다 — 옛 행과 새 행이 갈리면 나중에 읽는 사람이 이유를 알 수 없습니다

## 동아리 계층

대회·모임 위에 동아리(`clubs` · `club_members`)가 한 층 있습니다.
매주 모임을 열 때마다 초대 코드를 다시 뿌리는 일을 없애려고 만들었습니다.

```
clubs           동아리 (name · invite_code · owner)
club_members    재사용 명단 (club_id · user_id · display_name · role)
tournaments     + club_id  (nullable · on delete set null)
```

**핵심은 하나입니다 — 동아리는 명단의 원천이지 권한 축이 아닙니다.**

기존 권한 헬퍼 `is_tournament_member` / `is_tournament_admin` / `is_tournament_owner`
는 한 줄도 안 건드렸습니다. 동아리 운영진이 산하 대회를 만질 수 있는 근거는
"동아리 운영진이라서" 가 아니라 **대회를 만들 때 그 시점 운영진이 `admin` 멤버 행으로
함께 심어졌기 때문**입니다.

그래서 이런 비대칭이 생기고, 이건 버그가 아니라 위 원칙의 직접적 귀결입니다.

| 상황 | 결과 |
|---|---|
| 대회 생성 시점의 운영진 | 산하 대회에 `admin` 으로 들어가 있음 |
| **나중에** 운영진이 된 사람 | 그 전에 열린 산하 대회가 **목록에 안 보임** |
| 운영진에서 내려간 사람 | 안 끝난 산하 대회의 관리자 권한만 사라짐. 끝난 대회와 `tournament_members` 행은 그대로 |
| 동아리 밖 대회 | 동아리 운영진이라는 사실만으로는 아무 권한이 없음 |

`tournaments_select` 는 여전히 `is_tournament_member` 뿐입니다. **여기를 동아리로
넓히고 싶어질 때가 반드시 옵니다.** 넓히면 소속 없는 기존 대회 전부가 새 경로를 지납니다.
`db:smoke:club` 의 '추가' 절이 이걸 잡도록 걸어 뒀습니다 — 실패 문구에
"보이기 시작했다면 `tournaments_select` 가 동아리로 넓혀진 것" 이라고 적혀 있습니다.

### 호칭과 코드를 대회 쪽과 일부러 겹치지 않게 뒀습니다

| | 동아리 | 대회 |
|---|---|---|
| 역할 | 동아리장 · 운영진 · 회원 | 주최자 · 관리자 · 참가자 |
| 들어오는 문 | `/clubs/join` | `/join` |
| 코드 재발급 | **없음** — 바꾸면 아직 안 들어온 회원의 코드가 한꺼번에 죽습니다 | 있음 |

한 사람이 두 축에서 서로 다른 역할을 갖는 일이 정상이라, 같은 단어를 쓰면 지금 어느
축의 권한인지 흐려집니다. 코드도 마찬가지라 **한 칸에 둘 다 받는 통합 화면은 만들지
않습니다** — 누르기 전에는 어디로 들어가는지 알 수 없게 됩니다. 대신 각 화면 아래에
반대쪽으로 가는 줄을 하나 뒀습니다.

브루트포스 차단 카운터(`join_attempts`, 10분/10회)는 **두 코드가 공유합니다.**
그래서 안내 문구를 '동아리 코드를 10번' 으로 좁히지 않았습니다.

화면 쪽 판단(운영진인가 · 코드가 안 먹었을 때 뭐라고 말할 것인가)은
`src/lib/club.ts` 한 곳에 모여 있습니다. `src/lib/session.ts` 와 같은 이유입니다.

## 게스트 — 계정 없이 들어오고, 계정 없이 본다

동아리 회원이 아닌 사람이 상시 링크 하나로 그날 모임 명단에 스스로 들어오고,
로그인 없이 코트 현황과 자기 차례를 봅니다. 운영진 타이핑 0회.

```
clubs              + guest_code   22자 base32. invite_code(동아리 코드) 와 다른 코드다
tournament_members + is_guest     화면 배지·상한 계산 전용. 권한 판단에 안 쓴다

guest_sessions(p_code)                        anon. 오늘 후보 모임 목록 (필드 셋만)
join_as_guest(p_code, p_session_id, p_name)   anon. 등록
guest_board(p_code, p_session_id)             anon. 현황판 한 벌
rotate_guest_code(p_club_id)                  운영진 전용. 링크 회수
```

```
/g/CODE              이름 한 칸 → 그날 명단에 들어간다 (is_guest)
/g/CODE/모임id        코트별 현재 경기 · 대기열 · "내 차례까지 N경기"
```

**두 화면 다 로그인 가드 밖(`Public`)입니다.** `Protected` 로 옮기면 `RequireAuth`
가 먼저 `/login` 으로 돌려보내 **코트 앞에 선 게스트를 정확히 막습니다.**
현황판은 **아무것도 누를 수 없는 화면**입니다 — 경기로 들어가는 링크도, 코트를 잡는
뮤테이션도, 대기열 모달도 없습니다.

### 이 설계의 뼈대 일곱

**1. anon 에는 RLS 정책을 하나도 열지 않습니다 — 읽기도 예외가 아닙니다.**
`is_direct_api_call()` 은 `current_user = 'authenticated'` 하나로 정식 경로를 가르는데
anon 은 `'anon'` 이라 **거짓**이 됩니다. 그 순간 `guard_tournament_update` ·
`guard_member_update` · `guard_member_delete` 가 전부 "RPC 경로다" 로 오판해 통과합니다.
**붕괴는 롤에서 오지 동작 종류에서 오지 않습니다** — 읽기 정책 하나를 열어도 그 정책은
PostgREST 직접 조회에 그대로 열립니다. 비로그인 경로는 전부 **정책 0개 + SECURITY
DEFINER RPC** 로 갑니다.

**2. anon 이 부를 수 있는 public 함수는 정확히 넷입니다.** 게스트 RPC 셋 +
`is_direct_api_call()`. 넷째는 `20260819000001_fix_guard_permission.sql` 의 **의도된
결정**입니다 — 가드 트리거는 SECURITY INVOKER 여야만 발동하므로(DEFINER 로 바꾸면
`current_user` 가 `postgres` 가 되어 가드가 영영 안 걸립니다) 호출자 권한으로 불릴 수
있어야 합니다. **예전에 이 EXECUTE 를 걷었다가 주최자의 정상 수정이 통째로 막혔습니다.**
검사는 **개수가 아니라 집합**입니다 (`db:verify` · `db:smoke:guest` 81절) — 개수만 세면
하나가 빠지고 하나가 늘어난 교체를 못 잡습니다.

**3. 명단 전체는 절대 안 나갑니다 — 코트에 편성된 사람 이름만.** `tournament_members`
를 실으면 링크 하나로 그날 온 사람 **전원의 표시명**이 나가고, `profiles` 를 비공개로
지켜 온 것이 그 한 필드로 무의미해집니다. **필드를 하나 늘리는 것이 곧 노출 표면을
넓히는 것입니다** — 늘리려면 `20260829000001_guest_board.sql` 머리의 "안 싣는 것" 표를
먼저 고치고 smoke 73절(키 전수 검사)·74절(미편성 참가자 이름 부재)을 다시 통과시키세요.

**4. `match_overview` 뷰를 참조조차 하지 않습니다.** 뷰가 실어 나르는 필드가 싣기로
한 것보다 훨씬 많고, `security_invoker` 뷰의 권한 해석이 **함수 소유자에 따라
갈립니다.** 보안 경계를 배포 시점 값 위에 세우지 않습니다. 테이블을 직접 조인해
컬럼을 명시합니다.

**5. Realtime 은 원리적으로 못 씁니다.** 구독은 **구독 롤의 RLS 를 그대로 타므로**
anon 에 열려면 `matches` 에 anon 정책이 필요하고, 그 정책은 뼈대 1 과 똑같이 직접
조회에도 함께 열립니다. **폴링 10초**입니다 (앱 전역 `staleTime` 과 같은 값).
레이트리밋을 못 거는 경로라 탭이 안 보이면 멈추고, 끝난 모임에서는 폴링 자체를 세우고,
경기 목록에 limit 200 을 겁니다.

**6. 서버는 대기 순번을 세지 않습니다.** 셈법은 `schedule.ts` 의 `queuePosition` 과
SQL `notify_up_next` 둘뿐이고 **둘은 같은 줄을 세야 합니다.** 서버는 `queue_order` 만
싣고 정렬해서 보내고, 순번은 화면이 기존 `queuePosition` 으로 셉니다.

**7. 게스트가 적는 이름은 권한이 아닙니다.** localStorage 에만 있고(모임별 키 · TTL 36h)
서버로 보내지 않습니다 — `guest_board` 는 이름을 인자로 받지 않습니다. 쓰임은
**자기 경기 강조 하나**뿐이고, **이름이 없어도 현황판은 똑같이 전부 보입니다.**
이미 받은 목록과 문자열을 맞춰 볼 뿐이라 명단 탐색 도구가 되지도 않습니다 —
애초에 명단을 안 받기 때문입니다.

### 게스트가 쓰기를 못 하는 것은 코드 0줄로 이미 관철돼 있습니다

- **심판 불가** — `guard_referee_has_account` 가 `user_id is null` 인 멤버의 심판
  지정을 이미 거부합니다
- **점수 불가** — `is_match_player` 가 `tm.user_id = auth.uid()` 를 요구합니다.
  NULL 은 매칭되지 않고, `auth.uid()` 도 NULL 이면 `NULL = NULL` 은 true 가 아니라
  NULL 이라 `exists` 가 거짓입니다. 이중으로 안전합니다
- **나머지 RPC 불가** — anon 에게 grant 가 없습니다. 정책 이전에 grant 에서 끝납니다

`guest_board` 는 `stable` 로 선언돼 있어 **쓰기가 문법적으로도 막혀 있습니다.**
`volatile` 로 바꾸는 순간 그 방어가 사라지고, SECURITY DEFINER 안에서는
`is_direct_api_call()` 이 거짓이라 컬럼 가드 셋이 전부 우회됩니다.

### 화면이 틀리기 쉬운 자리

- **`match_overview` 에 anon SELECT grant 가 이미 있습니다** (Supabase 기본 권한,
  마일스톤 4 이전부터). 뷰가 `security_invoker=true` 라 **0행**이 나올 뿐입니다.
  **검사에서 403 을 기대하면 반드시 실패합니다** — 상태코드가 아니라 **반환 행 수**로
  판정하세요 (아래 「절대 깨면 안 되는 것 7」과 같은 규칙)
- **점수 표시를 `matches.scored` 로 판단하지 마세요.** `not null default true` 라
  점수를 한 번도 안 넣은 진행 중 경기도 참이고, 그렇게 판단하면 코트마다 `0 : 0` 이
  뜹니다. `score_a + score_b > 0` 으로 판단합니다 (`hasVisibleScore`)
- **코트 미배정 경기를 코트마다 복제하지 마세요.** 로그인 사용자 화면(`CourtBoard`)은
  이 줄을 모든 코트에 함께 띄웁니다 — 먼저 비는 코트가 집어가는 구조라 거기서는
  옳습니다. 게스트는 코트를 집어갈 수 없으므로 복제하면 **"대기 2번" 이 코트 넷에
  동시에 뜨고** 자기 차례를 네 번 센 것으로 읽습니다
- **코트가 아직 없는 내 경기에는 숫자를 내지 않습니다.** 어느 코트가 먼저 빌지 모르는데
  "앞에 2경기" 를 내면 추측이 아니라 거짓말입니다
- **`window.localStorage` 는 닿는 것만으로 던집니다** (사파리 프라이빗 등). 그 예외가
  새면 강조 하나 때문에 **현황판이 통째로 안 뜹니다.** 전부 try/catch 로 감싸고 실패는
  "이름 없음" 으로 떨어뜨립니다
- **저장하는 이름은 서버가 돌려준 최종 `display_name` 입니다.** 동명이인에게는
  `join_as_guest` 가 접미사를 붙이므로 입력 원문으로는 편성 목록과 매칭이 안 됩니다
- **오류를 갈라 주지 마세요.** 다른 동아리의 모임 · 대회 UUID · 시각 창 밖 · 없는 id ·
  코드 불일치가 **전부 `board_closed` 하나**입니다. 구별해 주면 임의 UUID 로 "이
  동아리에 이 모임이 있나" 를 캐는 탐색기가 됩니다
- **`user_id is null` 로 게스트를 판별하지 마세요.** `create_session` 이 미가입 회원
  (매주 오는 사람)도 심으므로, 그걸로 배지를 그리면 그 사람들 전원에게 게스트 딱지가
  붙습니다. `is_guest` 가 그 둘을 가릅니다
- **게스트 코드를 화면에 그리지 마세요.** 표시도 공유 버튼도 없습니다 — 화면 캡처 한
  장으로 그날 명단에 아무나 들어옵니다. 주소창에 이미 있는 것과, 복사하기 쉽게 놓아
  주는 것은 다릅니다

## 절대 깨면 안 되는 것

1. **점수는 원장 + 투영**
   `score_events` 에 append, `matches.score_a/b` 로 투영.
   `score_events` 에 쓰기 RLS 정책이 하나도 없는 건 의도입니다 — RPC 우회를 막습니다.
   `matches` 의 점수·상태·승자 컬럼도 트리거로 직접 수정을 막습니다.

2. **목표점수·승점은 `match_teams` 스냅샷**
   대회 도중 조커 구성을 바꿔도 지난 결과와 순위가 소급 변조되지 않습니다.

3. **`rules.ts` 와 `record_score` 는 같은 판정**
   화면용 사본입니다. 한쪽만 고치면 화면과 DB 가 어긋납니다.
   듀스가 붙은 뒤로는 `rules.ts` 의 `sideWins` ↔ SQL 의 `side_wins` 가 짝입니다.

3-1. **대기 순번의 정의도 두 곳에 있다**
   `schedule.ts` 의 `queuePosition` (화면의 대기 번호) ↔ SQL 의 `notify_up_next`
   (알림이 나가는 자리). 한쪽만 바꾸면 화면에 3번으로 보이는 사람에게 알림이 갑니다.
   **게스트 현황판도 같은 `queuePosition` 을 부릅니다** — 세 번째 셈법을 만들지
   마세요. 서버(`guest_board`)는 `queue_order` 만 싣고 순번은 세지 않습니다.

3-a. **'이 경기를 돌릴 수 있는 사람' 은 `can_run_match` 하나다**
   시작 · 코트잡기 · 득점 · 취소 · 종료가 같은 판단을 씁니다.
   모임에서만 '뛰는 사람' 이 열립니다 — `is_session_match AND is_match_player`.
   **'자기 경기' 가 핵심입니다.** 남의 코트 경기는 모임에서도 못 건드립니다.
   다섯 곳에 같은 OR 를 복사하면 나중에 한 곳만 고칩니다.

3-b. **`match_status` 를 늘리지 않는다**
   '그냥 끝' 은 `matches.scored` 로 표현합니다. status 를 보는 곳이
   여기저기(`get_standings` · `buildSchedule` · 기록 필터) 있어서, 값을 하나
   늘리면 그 전부가 새 값을 모르는 채 지나가고 **어디에도 안 뜨는 경기**가 생깁니다.

3-2. **경기 규칙은 편성 시점에 `match_teams` 로 굳는다**
   목표 점수 · 승점 · 듀스 · 상한 네 가지입니다. `match_teams_fill_rules` 트리거가
   채우므로 편성 함수(create_match · update_match · record_manual_match)는
   새 규칙이 늘어도 손댈 필요가 없습니다.
   설정을 바꾸면 **아직 시작 안 한 경기만** 다시 굳습니다.

4. **대기 큐의 진실은 ref 하나**
   `useMatchScoring` 에서 localStorage 는 거울, state 는 렌더용입니다.
   셋을 섞어 읽으면 저장 실패 환경(사파리 시크릿)에서 큐가 쪼그라듭니다.

5. **낙관적 점수를 따로 세지 않는다**
   `pending` 에서 파생합니다. 별도 카운터를 두면 실시간 갱신과 경쟁해 이중 계산됩니다.

6. **`join_club` · `join_tournament` 은 예외 대신 봉투를 돌려준다**
   `raise exception` 은 같은 트랜잭션의 기록도 되돌립니다. 실패를 예외로 던지면
   방금 남긴 브루트포스 시도 기록까지 함께 롤백돼 **차단 카운터가 영원히 0** 이 됩니다.
   이 저장소가 이미 한 번 밟은 함정입니다.
   그래서 두 함수는 jsonb 봉투(`ok` / `rate_limited` / `bad_format` / `not_found`)를
   반환합니다. 봉투를 푸는 곳은 `src/lib/club.ts` 의 `parseJoinResult` **한 곳**입니다 —
   페이지마다 풀면 안내 문구가 화면마다 흩어집니다.
   `parseJoinResult` 가 인자를 `JoinClubResult` 가 아니라 `unknown` 으로 받는 것도 의도입니다.
   타입대로 받으면 'ok:true 인데 club 이 안 실려 온' 경우를 못 잡고, 화면이
   `/c/undefined` 로 이동해 사용자가 "코드가 틀린 건지 앱이 깨진 건지" 모르는 자리에 남습니다.
   차단된 시도는 기록하지 않습니다 — 기록하면 재시도할 때마다 10분 창이 스스로 밀려
   영구 차단이 됩니다. 카운터는 임계치 10에서 멈추는 게 맞습니다.

7. **PostgREST 는 RLS 로 0행이 걸러져도 200/204 를 준다**
   권한 없는 수정이 화면에는 **'성공' 으로 보입니다.** 변경의 성패는 HTTP 상태가 아니라
   **반환 행**으로 판정해야 합니다.
   `renameClub` 은 `.select('id').single()` 로 받아 0행이면 던지고, `deleteClub` 은
   반환 행 수를 셉니다. 나머지는 예외를 던지는 RPC 라 해당 없습니다.
   `.update()` / `.delete()` 를 새로 쓸 때마다 이 판정을 같이 넣으세요.

8. **대회 명단은 동아리 명단의 복제(스냅샷)이지 참조가 아니다**
   대회를 만들 때 동아리 회원을 `tournament_members` 로 **복사해 심습니다.**
   참조로 두면 지난 대회의 이름이 동아리의 *현재* 이름을 가리키게 되고,
   그때 그 사람이 뭐라고 불렸는지는 복원할 수 없습니다. 동아리에서 사람을 빼도
   산하 대회의 출전 기록은 남습니다 — **명단에서 사라지는 것과 기록이 지워지는 것은
   다른 일입니다.**
   복사할 때 이름 충돌은 `unique_display_name` 이 **자르고 접미사를 붙여** 해결합니다
   (20자 제한이라 붙이기 전에 자릅니다). 어떤 경우에도 실패하지 않습니다 —
   운영진 동명이인 때문에 대회 생성이 통째로 실패하면 안 되기 때문입니다.

## 이 프로젝트에서 배운 함정

- **`interface` 로 뽑은 Row 는 `Record<string, unknown>` 에 할당되지 않는다.**
  supabase-js 스키마 인식이 통째로 실패하고 `.rpc()` 가 조용히 `any` 가 됨.
  `database.typetest.ts` 가 지킵니다.
- **`raise exception` 은 같은 트랜잭션의 기록도 되돌린다.**
  브루트포스 차단 카운터가 영원히 0 이었습니다. → 예외 대신 결과 반환.
- **RLS 는 행 단위라 컬럼을 못 가린다.**
  admin 이 `owner_id` 를 바꿔 대회를 탈취할 수 있었습니다. → BEFORE 트리거.
- **JSX 에서 `배열.length && ...` 는 길이가 0 일 때 `0` 을 출력한다.**
- **async 본문이 동기적으로 끝나면 `finally` 가 변수 할당보다 먼저 돈다.**
- **뷰 컬럼은 Postgres 가 NOT NULL 을 보존하지 않는다** → 생성 타입이 전부 nullable.
- **함수를 다시 만들 때 '최신' 을 잘못 짚으면 검사가 조용히 사라진다.**
  `start_match` 를 20260818000011 에서 복사했는데 실제 최신은 20260819000003
  이었다. '한 사람이 두 코트에서 동시에' 검사가 통째로 빠졌고
  `db:smoke:match` 가 잡았다. 고칠 함수는 `grep -ln "function 이름"` 으로
  **전부** 찾아 마지막 파일을 봐야 한다.
- **`not null default true` 인 컬럼은 "설정됐다" 를 뜻하지 않는다.**
  `matches.scored` 로 "점수를 보여줄까" 를 판단하면 점수를 한 번도 안 넣은 진행 중
  경기도 참이라 코트마다 `0 : 0` 이 뜬다. 기본값이 있는 플래그로 **사용자의 행위
  여부**를 판단하지 말 것 — 실제 값(`score_a + score_b > 0`)을 봐야 한다.
- **확장이 설치돼 있는 것과 내 `search_path` 에서 보이는 것은 다른 말이다.**
  Supabase 는 pgcrypto 를 `public` 이 아니라 `extensions` 스키마에 설치한다.
  `gen_random_uuid()` 는 PG13+ 코어 내장이라 멀쩡히 돌아 더 늦게 드러난다.
